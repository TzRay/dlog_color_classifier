# 色彩模式识别优化方案

## 1. 结论摘要

引用任务对“现有规则会输出什么”的判断是正确的，但对“素材本身是否能够确认”的结论不完整。

当前程序只读取 `djmd` 第一包，并使用以下规则：

- `ColorGammaSxS` 枚举为 `22`：D-Log2；
- `ColorGammaSxS` 枚举为 `2`：D-Log；
- 枚举缺失且 `record_mode == 8`：普通 Rec.709；
- 其他情况：无法确认。

因此，0066、0067、0071 按当前算法确实都会成为“无法确认”。但是，这三支文件的
QuickTime `mdta` 元数据中均存在结构化的 `ColorGammaSxS` 文本标签：

| 文件 | 当前 `djmd` 结果 | `mdta` 明确标签 | 正确结论 |
| --- | --- | --- | --- |
| 0066 | 枚举缺失，`record_mode=10` | `Rec.709` | 普通 Rec.709 |
| 0067 | 枚举 `9`，`record_mode=10` | `Rec.2100 HLG` | HLG HDR |
| 0071 | 枚举缺失，`record_mode=10` | `Rec.709` | 普通 Rec.709 |

上述三个标签也已使用 `ffprobe` 独立读取
`com.dji.camera.ColorGammaSxS` 后交叉验证，并非来自压缩码流中的关键词碰撞。

同一测试目录的 9 支素材都带有明确的 `mdta` 标签。以该标签为基准，0064、0065、
0068、0069、0070、0072 的现有分类结果均正确，只有上述 3 支因证据源单一而落入未知。

优化目标不是简单增加一条“枚举 9 等于 HDR”的规则，而是让程序优先读取容器内的
明确色彩标签，并将 `djmd` 枚举和 `record_mode` 改为补充证据。

## 2. 对引用任务证据链的评价

### 2.1 正确之处

1. 准确复现了当前分类器的结果和规则优先级。
2. 没有仅凭文件名 `_D` 猜测色彩模式，保留“无法确认”比误分类更安全。
3. 没有在缺少映射依据时直接把 `ColorGammaSxS=9` 写入正式规则。

### 2.2 需要纠正之处

1. “现有算法无法确认”不等于“文件无法确认”。文件自己的 `mdta` 键已经给出明确答案。
2. 在文件头尾原始字节中搜索 `HLG`、`D-Log` 等短字符串不能作为可靠证据。扫描范围包含
   压缩视频码流，三个字母的随机命中概率很高；只有位于合法 `moov/meta/keys/ilst/data`
   结构中的值才能视为元数据。
3. 当前诊断脚本按固定尾部 8192 字节、可打印字符串顺序取第三个值，适合临时取证，
   不适合进入生产分类路径。`moov` 位置、box 长度、键顺序和附加字段都可能变化。
4. 0067 已能由 `mdta` 确认为 `Rec.2100 HLG`。枚举 `9` 在这支 PP-041 样本中与 HLG
   对应，但要把它用作“缺少 `mdta` 时的全局兜底”，仍需跨机型和固件验证。

## 3. 目标与约束

### 3.1 目标

- 正确识别 D-Log、D-Log2、Rec.709、Rec.2100 HLG 和无法确认。
- 保留所有原始证据及来源，让用户能理解判定过程。
- 证据冲突时停止自动整理，避免静默误分类。
- 不解码视频画面，不依赖外部可执行程序，继续保持轻量和可移植。
- 保持现有 CLI、GUI、报告及整理流程的向后兼容性。

### 3.2 暂不纳入

- 通过画面亮度、直方图或机器学习反推色彩模式。
- 仅凭 `_D` 文件名、LUT 数据存在与否或码流中的短字符串分类。
- 未经样本集验证便建立跨所有 DJI 机型通用的私有枚举表。

## 4. 推荐架构

### 4.1 新增结构化 QuickTime `mdta` 读取器

在核心层新增独立模块，例如 `core/quicktime_metadata.py`，解析以下结构：

```text
moov
└── meta（或 udta/meta）
    ├── keys
    │   └── mdtacom.dji.camera.ColorGammaSxS
    └── ilst
        └── 对应键索引/data
            └── D-Log | D-Log2 | Rec.709 | Rec.2100 HLG
```

实现要求：

- 按 ISO BMFF box 边界读取，支持 32 位大小、`largesize` 和 `size=0`；
- 正确处理 `meta` FullBox 的 version/flags 前缀；
- 用 `keys` 的一基索引关联 `ilst` 子项，不依赖固定键顺序；
- 只读取目标 `data` payload，不读取或扫描 `mdat`；
- 支持 `moov/meta` 与 `moov/udta/meta` 两种常见位置；
- 对非法长度、未知数据类型和非 UTF-8 值返回中文诊断，不越界读取；
- 不使用“读取文件最后 N 字节”的启发式实现。

现有 MP4 box 基础能力可复用，但应把“解析 box 树”和“读取 djmd 第一包”解耦，避免
同一文件重复解析 `moov`。

### 4.2 将证据建模为多个信号

当前 `ClassificationEvidence` 只有两个 `djmd` 数值，无法表达文本标签、来源、置信度和
冲突。建议增加结构化信号，至少包含：

- `source`：`quicktime_mdta`、`djmd_gamma_enum`、`djmd_record_mode`；
- `raw_value`：保留原始字符串或整数；
- `inferred_mode`：该信号对应的色彩模式；
- `strength`：`explicit`、`mapped`、`heuristic`；
- `warning`：解析异常、未知值或证据冲突说明。

对外报告继续保留现有字段，并在末尾追加“元数据标签”“主证据来源”“置信度”“冲突说明”，
避免破坏依赖原 CSV 列名的流程。

### 4.3 扩展色彩模式

在 `ColorMode` 中新增稳定值 `REC2100_HLG = "rec2100_hlg"`，显示名使用
“Rec.2100 HLG（HDR）”。不要把 HLG 合并到 Rec.709 或“无法确认”。

首个版本建议：

- 报告、统计、筛选和 GUI 表格显示 HLG；
- 移动/复制模式支持目标目录 `hlg/`；
- 前缀模式为 HLG 使用 `hlg_`，与 D-Log 和 D-Log2 的前缀策略一致；

### 4.4 分类决策表

| 条件 | 结果 | 置信度/处理 |
| --- | --- | --- |
| `mdta` 标签为已知值，且其他证据一致或缺失 | 使用 `mdta` 结果 | 高 |
| `mdta` 标签已知，但与已映射的 `djmd` 枚举冲突 | 无法确认 | 标记“元数据冲突”，禁止自动整理 |
| 无 `mdta`，`djmd` 枚举为 `22` | D-Log2 | 中 |
| 无 `mdta`，`djmd` 枚举为 `2` | D-Log | 中 |
| 无 `mdta`，枚举缺失且 `record_mode=8` | Rec.709 | 低，标明“兼容规则” |
| 无 `mdta`，`djmd` 枚举为经样本集确认的 `9` | Rec.2100 HLG | 中；完成跨机型验证后启用 |
| 其余情况 | 无法确认 | 展示全部原始值 |

标签规范化只接受明确白名单，例如大小写和两端空白可归一化，但未知文本不得模糊匹配：

- `D-Log` → D-Log；
- `D-Log2` → D-Log2；
- `Rec.709` → Rec.709；
- `Rec.2100 HLG` → Rec.2100 HLG。

### 4.5 错误语义

- 文件不可读、容器严重损坏：`ERROR`；
- 文件可读但没有任何可用色彩证据：`UNKNOWN`；
- 两个可靠证据互相冲突：`UNKNOWN`，附冲突原因；
- 某个证据源解析失败、另一个明确证据源成功：允许分类，但保留警告。

这样可以避免“没有 djmd 轨”覆盖掉本来可从 `mdta` 成功得到的结果。

## 5. 实施阶段

### 阶段 A：建立可验证基线

1. 将 9 支样本的最小元数据结构提取为不含视频画面的测试 fixture，避免测试依赖桌面路径和
   数十 MB 原始文件。
2. 记录当前结果、`mdta` 期望值、`djmd` 原始值、机型 PP-041 和固件相关字段。
3. 对现有 2026 样本报告生成“标签覆盖率、枚举分布、冲突数”统计；不得把文件名相同但日期
   不同的素材混为同一条样本。

### 阶段 B：实现读取器和证据模型

1. 扩展 MP4 box 解析层并实现 `keys/ilst/data` 的结构化读取。
2. 新增多信号证据结构，同时为旧报告字段提供兼容输出。
3. 将文件级分类改成“一次打开文件、一次解析容器、分别尝试 mdta 与 djmd”。

### 阶段 C：启用新分类和 HLG

1. 按决策表合并信号，优先采用明确 `mdta` 标签。
2. 新增 HLG 模式，并同步 CLI、GUI、报告、筛选、统计、目录规划和用户文档。
3. 冲突结果禁止执行自动重命名、移动或复制，并在界面突出显示。

### 阶段 D：校准私有枚举兜底

1. 按相机型号、固件版本、文本标签统计 `djmd` 枚举映射。
2. 只有当枚举 `9` 在足够多、互相独立的样本中始终对应 `Rec.2100 HLG`，才将其加入
   无 `mdta` 文件的兜底表。
3. 枚举映射表应集中定义，并记录样本数量、适用机型/固件和首次验证版本，避免散落在条件分支中。

## 6. 测试方案

### 6.1 单元测试

- `keys` 与 `ilst` 正确按索引关联，而非按字符串出现顺序关联；
- `meta` FullBox、`udta/meta`、64 位 box、未知 box、截断 box；
- 四个已知文本标签及未知标签；
- `mdta` 明确、`djmd` 缺失；
- `mdta` 缺失、`djmd` 枚举可识别；
- `mdta` 与 `djmd` 冲突；
- `djmd` 缺失但 `mdta` 可用时不应返回 `ERROR`；
- HLG 在报告序列化、统计、筛选和目录规划中的行为。

### 6.2 回归测试

测试目录 9 支素材的期望结果：

| 文件编号 | 期望结果 |
| --- | --- |
| 0064、0070、0072 | D-Log |
| 0065 | D-Log2 |
| 0066、0068、0069、0071 | Rec.709 |
| 0067 | Rec.2100 HLG |

### 6.3 性能与安全

- 扫描不读取 `mdat` payload，文件读取量应与 `moov`/目标 metadata 大小同阶；
- 同一批素材相对旧实现的总扫描耗时增长不超过 20%；
- dry-run、冲突策略、撤销清单和目标路径校验保持现有行为；
- 未知或冲突素材不得因新增模式而被自动重命名。

## 7. 验收标准

1. 9 支回归样本全部匹配结构化 `mdta` 标签，“无法确认”由 3 支降为 0 支。
2. 0066、0071 输出 Rec.709；0067 输出 Rec.2100 HLG（HDR）。
3. 原先正确的 6 支素材无回归。
4. 人工构造的 `mdta`/`djmd` 冲突样本输出“无法确认”，报告能同时看到两份原始证据。
5. 没有 `djmd` 但有合法 `mdta` 的样本仍能成功分类。
6. CLI、GUI、CSV、JSON 和整理规划均能表示 HLG，旧报告字段仍存在。
7. 全量自动化测试通过，新增解析器对畸形 box 有边界检查，不扫描压缩码流寻找关键词。

## 8. 推荐优先级

最高优先级是结构化 `mdta` 读取器、证据冲突处理和 9 支样本回归测试。随后再扩展 HLG 的
界面与整理能力。把枚举 `9` 写成跨机型通用规则应放在最后，因为明确标签已经能解决本次
误判，而未经校准的私有枚举兜底可能引入新的静默错误。
